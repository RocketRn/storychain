# Decisions

One line per decision: decision — reason.

- pnpm workspaces + Node 20+ (dev machine runs 22) — boring, as requested.
- ESLint 9 flat config at repo root — single lint entry point for all packages.
- Shared package is consumed from source (`main` points to `src/index.ts`) — no build step needed in dev; API runs via `tsx`, web via Vite.
- Money is always bigint/string smallest units — no float math.
- API runs in prod via `tsx` (no emit) — shared package is TS source; avoids a bundling step. `build` = typecheck.
- Prisma 6 (not 7) — 7 changes client/config setup; 6 is stable and works with both SQLite and PostgreSQL.
- No Prisma enums; enum-like columns are Strings validated by zod — keeps SQLite/PostgreSQL parity.
- SQLite files get `connection_limit=1` appended automatically — SQLite has a single writer; pooled connections cause SQLITE_BUSY under concurrency.
- Postgres migrations are provider-specific: when switching provider, delete `prisma/migrations` and run `prisma migrate dev --name init` against Postgres (documented in README).
- Auth is two-layer: a global `onRequest` hook sets `request.user` (so rate limits can key on user id), `requireAuth` preHandler enforces — avoids unauthenticated requests being keyed per user.
- Users are auto-created on first authenticated request (not only via /auth/session) — concurrent first requests are handled (P2002 re-read).
- Chain lists use offset cursors (opaque number) — simple and fine at this scale; gallery uses keyset cursor on `position`. "trending" = postsCount desc, then newest.
- Gallery order is newest first (position desc).
- Re-posting to a chain counts as a publication for the daily limit (conservative) and keeps the original position; it never un-hides a moderated post.
- Daily limit: cheap pre-flight check before image processing, authoritative atomic conditional increment inside the DB transaction; failed validations never consume quota. Orphaned uploaded files after a lost race are accepted (unique keys, harmless).
- Server watermark is a text pill rendered with a bundled OFL font (Inter Bold, `apps/api/assets/fonts`) placed 220px above the bottom edge — sits above the ~250px bottom band so the Telegram story UI does not cover it.
- Uploads accepted: JPEG/PNG only, exactly 1080x1920, re-encoded to JPEG q90 (metadata stripped); thumbnail 360px wide.
- Demo/dev identities: telegramId 1000000+N = `?mock_user=N`; seed creates users 1000001..1000004. Seeded chains have fixed ids (cat00001, desk0002, trk00003).
- Platform method flag lives in `packages/shared/src/plans.ts` (`allowedMethods`): Stars only on ios/android unless `TON_PAYMENTS_ALL_PLATFORMS=true`. Owner must verify against current Telegram rules.
- Web uses `react-router-dom` v6 (BrowserRouter) + TanStack Query v5; no Zustand — server state lives in Query, the little UI state is local/hooks.
- `tg` facade is a Proxy over the real/mock implementation chosen once in `initTelegram()`; components never touch `window.Telegram`.
- Mock is selected by the build-time constant `import.meta.env.VITE_DEV_MOCK === "true"` and loaded through dynamic `import()` — Vite drops it (and MockUI/DevTools) from production bundles (verified by grepping `dist`); `vite.config.ts` additionally fails any production-mode build with the flag on.
- Mock identity (`mock_user`, `mock_premium`, `mock_platform`, `mock_lang`) is persisted in localStorage so SPA navigation and DevTools switches survive reloads; query params override it when present.
- Greeting/name displayed in UI comes from the server session (authoritative), not from client-side initDataUnsafe.
- Mock initData is signed at page load and is valid for 1h (server maxAge); the mock does not auto-refresh — reload the page after an hour.
- API base in the web app is same-origin `/api` (Vite proxy in dev, Fastify single-origin in prod); `VITE_API_URL` is optional.
- E2E uses its own SQLite file + upload dir, API on :3100 and web on :5273 (single origin via the Vite proxy), recreated on every run. The sandbox's preinstalled Chromium is used via `executablePath` (override with `PW_CHROMIUM`).
- Seed removes the demo users' DailyUsage rows so seeding never consumes their daily quota.
- Fonts: 6 self-hosted OFL families from @fontsource (latin + cyrillic subsets, one weight each; files + license texts in `apps/web/public/fonts`). Free: Inter, Manrope. Premium: Unbounded, Oswald, Playfair Display, Pacifico. Chosen because all cover Cyrillic — Bebas Neue / Space Grotesk (first draft) do not, and canvas would silently fall back for Russian titles.
- `document.fonts.load(font, sampleText)` is awaited with the real text before any drawing so the right unicode-range subset is fetched.
- Server enforces premium templates AND premium fonts (client sends the optional `fontFamily` form field; premium font + non-PRO -> `PRO_REQUIRED`). The font is not stored; it only gates the request since the card is rendered client-side.
- Editor step 1 ("pick/create chain") happens on Home/Chain/Create screens; the editor opens with the chain already chosen and shows it in its header. Steps in the editor: Photo -> Style (pan/zoom + template/font picker) -> Publish (preview + caption).
- "#N" badge and participants counter both use `myPosition ?? postsCount + 1` (API returns `myPosition` so re-posting keeps the same number).
- Live preview is a 540x960 canvas drawn with the same `drawCard` as the export (scale 0.5); the free-user watermark is a DOM overlay positioned like the server's (bottom-right, 220px above the bottom edge).
- Export: JPEG q0.9, lowered stepwise (0.82/0.74/0.66) only if the blob exceeds 3 MB. Photos > 2560px on the longest side are downscaled right after decoding (EXIF handled by `createImageBitmap({imageOrientation:"from-image"})`).
- Pan/zoom model: `View = {zoom>=1, cx, cy}` (normalized source center) so the photo can never leave the frame; drag, pinch, wheel and a zoom slider (accessible) all go through the same pure helpers in `editor/layout.ts` (unit tested). Frame rotation (±3° on two templates) is ignored for drag math.
- The Editor chunk (canvas, fonts CSS, templates UI) is lazy-loaded; a test hook (`window.__storychain.render`) exists only when `VITE_DEV_MOCK=true`.
- Playwright sample photos are generated with `sharp` (root devDependency) so EXIF-rotated JPEGs can be produced deterministically.
- Known: main bundle is ~150 kB gzip (react-router, react-query, zod via shared); TonConnect will be code-split in Phase 5; further bundle work is in Phase 6.
- `widget_link` is Premium-only in Telegram Stories: it is passed only when `initDataUnsafe.user.is_premium` is true, the link is ALWAYS also in the caption text, and if shareToStory throws with a widget we retry once without it (we cannot reliably detect the rejection otherwise).
- `shareToStory` requires a public HTTPS media URL (blob/data URLs do not work) and client >= 7.8: below that (or on a throw) we fall back to opening/downloading the image + copying the link + an alert. `sharedToStory` is set only after a real shareToStory call, never for the fallback.
- Story text is capped at 200 chars (safe for non-Premium authors): the title is shortened first, the link is never cut. Length is counted in UTF-16 units (conservative vs. code points).
- Publishing auto-opens the story composer ("one tap"); the done screen and the chain page offer "Share again" and "Send to chat" (`t.me/share/url` via `openTelegramLink`) without re-posting; the API returns `myPost` and `shareLink` on `GET /chains/:id` for this.
- Bot: `/start` replies with a `web_app` inline button; `/start chain_<id>` opens `WEBAPP_URL/?tgWebAppStartParam=chain_<id>` (a web_app button cannot carry `startapp`, so the client's start_param fallback reads that query param). Invalid payloads fall back to the plain welcome. Telegram requires https for web_app buttons.
- The bot is started only when `BOT_ENABLED=true` (default on in production, off otherwise) so mock/dev needs no real token. Polling in dev (deletes any webhook first), webhook in prod at `POST /api/telegram/webhook` verified with the secret-token header (grammY `secretToken`). Handlers are unit tested by replacing the Bot API transport with a recorder.
- Mock: `showAlert`/`showConfirm` are DOM dialogs and `openTelegramLink` is a modal (scriptable in e2e); DevTools has a "Legacy client (<7.8)" switch to exercise the manual fallback.
- The clipboard write is raced against a 1.5s timeout: the Clipboard API can hang on a pending permission prompt and must never block the fallback alert.
- The Vite dev server allows any Host header (`allowedHosts: true`) so one tunnel to :5173 serves web + `/api` + `/uploads` through its proxy; this affects the dev server only.
- Payments are provider-agnostic at the ledger level (`payments/ledger.ts`): `settlePayment` = conditional claim (pending|expired -> paid) + PRO extension + Subscription row in ONE DB transaction; `externalId` (Stars charge id / TON event id) is unique, so replays and double deliveries grant exactly once. Verified with concurrent-delivery tests.
- PRO grant extends from `max(now, proUntil)` by the plan's 30 days; a refund revokes exactly one period (`proUntil -= 30d`, Subscription row deleted) and is idempotent.
- Stars: invoice link via `createInvoiceLink` (XTR, empty `provider_token`, one price item, `payload = reference`). `pre_checkout_query` is answered from one indexed DB lookup (no network) and validates status/expiry/amount/currency/user. `successful_payment` with a mismatching amount or user is NOT granted and is logged loudly (money moved: manual review). `refunded_payment` service messages revoke PRO; `scripts/refund.ts` (`pnpm --filter @storychain/api refund <reference|chargeId>`) calls `refundStarPayment` first, then revokes locally.
- The client's `openInvoice` status is never trusted: after `paid`/`pending` the paywall polls `GET /api/payments/:reference` (Stars 20 s, TON 150 s). A timeout is shown as "still processing" with a re-check button, not as failure.
- Without a bot (mock/dev) the invoice URL is `mock-invoice://<reference>`; the mock dialog's "Pay" goes through `POST /api/dev/payments/:reference/complete`, which calls the SAME `handleSuccessfulPayment` code as the bot (so amount/user validation is exercised). For TON the dev endpoint settles directly (it stands in for "the verifier matched an on-chain transfer").
- TON verification: a transfer pays a transaction iff comment == reference, status ok, jetton master and recipient equal in RAW form (`Address.parse(..).toRawString()`, so bounceable/non-bounceable/testnet spellings are equal), amount >= expected (overpay accepted, underpay stays pending), tx hash not used before, and timing is sane. Event timestamp must not precede the order (minus 5 min skew).
- Late TON payments: a transfer after `expiresAt + 5 min skew` is still honored (and logged as late) if it happened within 24 h of expiry — the user paid real money and refusing would strand it; beyond that the tx stays `expired` and is only logged for manual handling. `expired` is a status (set by the polling job / shown by the API), not a tombstone.
- The poller (`setInterval` 10 s, shared in-flight promise as overlap guard) skips the indexer entirely when no TON order is open, to save TonAPI quota. It looks back to the oldest open order, up to 5 pages x 100 events. `POST /payments/ton/confirm` runs the same tick immediately (BOC is informational only, never trusted).
- TonAPI endpoints/response shapes used (ASSUMPTION — re-verify against current TonAPI docs and with the manual mainnet test): `GET /v2/accounts/{merchant}/jettons/{master}/history` (AccountEvents with `JettonTransfer` actions; `event_id` is used as the tx hash / idempotency key), `GET /v2/accounts/{owner}/jettons/{master}` (-> `wallet_address.address`), `GET /v2/jettons/{master}` (-> `metadata.decimals/symbol`). All sit behind the `TonIndexer` interface (`payments/tonIndexer.ts`); parsing is unit-tested on fixtures.
- GRAM is assumed to follow TEP-74: an ordinary transfer with `forward_ton_amount > 0` makes the merchant's Jetton wallet emit a transfer notification carrying the forward payload (our reference). If GRAM (a PoW jetton) deviates, comment matching would fail — hence the manual small mainnet test transfer in `CHECKLIST.md`.
- Startup self-check (`tonStartupCheck.ts`): runs only when a merchant address is configured and not in mock mode. It parses addresses with `@ton/core`, refuses to start if the jetton's on-chain `decimals` differ from `GRM_DECIMALS`, and only warns on symbol mismatch.
- Only `@ton/core` is used (cell building/parsing); `@ton/ton` was not needed, so it is not a dependency. The browser needs a `Buffer` polyfill (`ton/polyfill.ts`), imported first by every TON module.
- Client payload: ONE message to the sender's own Jetton wallet (0.05 TON gas) with body `transfer#0f8a7ea5` (query_id random uint64, amount, destination = merchant OWNER address, response_destination = sender, no custom payload, forward_ton_amount 0.01 TON, forward payload = Either-ref text comment `0x00000000 + reference`), `validUntil` = now + 10 min; tested by decoding the BOC back.
- The sender's Jetton wallet is resolved by the backend (`GET /api/ton/jetton-wallet`, cached 10 min per raw owner address) so no third-party API key ever reaches the browser. TonConnect and `@ton/core` live in a lazy chunk used only on the paywall and only in non-mock builds; the mock build uses a simulation panel instead.
- `tonconnect-manifest.json` is generated from `WEBAPP_URL` by `predev`/`prebuild` (wallets need the real public origin) and is git-ignored; `iconUrl` points at `/icon-180.png`.
- Platform policy flag: `TON_PAYMENTS_ALL_PLATFORMS=false` => Stars only on ios/android (enforced by `/api/plans` AND `/api/payments/ton/intent`, so the policy cannot be bypassed by calling the API directly). The owner must verify against current Telegram rules for digital goods in Mini Apps.
- E2E additionally runs a second Vite server with `VITE_DEV_MOCK=false` and a fake `window.Telegram.WebApp`, so the real (non-mock) facade and lazy TonConnect chunk are exercised on every run.
- Single-origin mode: with `SERVE_WEB=true` (default in production) Fastify serves `apps/web/dist`, falls back to `index.html` for non-`/api`, non-`/uploads` GETs (client-side routes / deep links) and keeps unknown `/api/*` as JSON 404s. It refuses to start if the build is missing. Static assets are exempt from the rate limiter (many files per load, shared NAT IPs).
- CSP in single-origin mode: `script-src 'self' https://telegram.org` (the SDK), inline styles allowed (React style props + TonConnect), `img-src https: data: blob:`, `connect-src 'self' https: wss:` (wallet bridges), `frame-ancestors 'self' https://web.telegram.org https://*.telegram.org`; `X-Frame-Options` is disabled because it cannot express the Telegram Web allowance (Mini Apps are iframed there). `upgrade-insecure-requests` only in production so plain-http local runs work.
- `INITDATA_MAX_AGE_SEC` defaults to 24 h (the pure `validateInitData` keeps the spec's 3600 s default): Telegram does not refresh `initData` while a Mini App stays open, so a 1 h window logs people out mid-session. The trade-off is a longer replay window for a leaked header; tighten it if you prefer.
- `TRUST_PROXY` is opt-in so a spoofed `X-Forwarded-For` cannot dodge IP rate limits when the API is directly exposed.
- `pnpm build` forces `VITE_DEV_MOCK=false` (cross-env) so a dev `.env` can never produce a production build with the mock, while a direct `vite build` with the flag on still fails loudly (guard kept in `vite.config.ts`). `pnpm smoke` greps the built bundle for mock/test-hook markers.
- The web app imports `@storychain/shared/light` (everything except the zod schemas), saving ~7% of the main bundle; client-side chain validation mirrors the server schema through `normalizeChainInput` (a unit test asserts they agree). The server keeps using the full `@storychain/shared`.
- The TonConnect chunk loads only after the user taps "Pay with GRM" (and is preloaded on hover/focus), so Stars-only users never download it.
- A11y: axe (WCAG 2 A/AA) runs in e2e over Home, Chain, Create, Paywall, Profile and Editor in light and dark; it found sub-4.5:1 hint/button/link colors in the fallback palette and the mock theme, which were darkened. Real Telegram themes bring their own colors, so contrast there is Telegram's responsibility.
- Mobile layout is asserted at 390×844 with touch emulation (no horizontal overflow on every screen; editor preview ≤ 60% of the viewport height, 9:16 preserved).
- Profile ("My posts") is a minimal screen backed by `GET /api/me/posts` (offset cursor, hidden posts/chains excluded) reachable from the avatar on Home.
- `pnpm setup` (scripts/setup.mjs) is the one-command bootstrap: `.env` from the example (mock mode), Prisma generate, migrate, seed.
