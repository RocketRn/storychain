# Decisions

One line per decision: decision — reason.

- pnpm workspaces + Node 20+ (dev machine runs 22) — boring, as requested.
- ESLint 9 flat config at repo root — single lint entry point for all packages.
- Shared package is consumed from source (`main` points to `src/index.ts`) — no build step needed in dev; API runs via `tsx`, web via Vite.
- Money is always bigint/string smallest units — no float math.
- API runs in prod via `tsx` (no emit) — shared package is TS source; avoids a bundling step. `build` = typecheck.
- Prisma 6 (not 7) — 7 changes client/config setup; 6 is stable and works with both SQLite and PostgreSQL.
- No Prisma enums; enum-like columns are Strings validated by zod — keeps SQLite/PostgreSQL parity.
- SQLite files get `connection_limit=1` appended automatically — SQLite has a single writer; pooled connections cause SQLITE_BUSY under concurrency.
- Postgres migrations are provider-specific: when switching provider, delete `prisma/migrations` and run `prisma migrate dev --name init` against Postgres (documented in README).
- Auth is two-layer: a global `onRequest` hook sets `request.user` (so rate limits can key on user id), `requireAuth` preHandler enforces — avoids unauthenticated requests being keyed per user.
- Users are auto-created on first authenticated request (not only via /auth/session) — concurrent first requests are handled (P2002 re-read).
- Chain lists use offset cursors (opaque number) — simple and fine at this scale; gallery uses keyset cursor on `position`. "trending" = postsCount desc, then newest.
- Gallery order is newest first (position desc).
- Re-posting to a chain replaces the previous post, keeps its original position and never un-hides a moderated post; it is free like everything else on posting.
- Server watermark is a text pill rendered with a bundled OFL font (Inter Bold, `apps/api/assets/fonts`) placed 220px above the bottom edge — sits above the ~250px bottom band so the Telegram story UI does not cover it.
- Uploads accepted: JPEG/PNG only, exactly 1080x1920, re-encoded to JPEG q90 (metadata stripped); thumbnail 360px wide.
- Demo/dev identities: telegramId 1000000+N = `?mock_user=N`; seed creates users 1000001..1000004. Seeded chains have fixed ids (cat00001, desk0002, trk00003).
- Platform method flag lives in `packages/shared/src/plans.ts` (`allowedMethods`): Stars only on ios/android unless `TON_PAYMENTS_ALL_PLATFORMS=true`. Owner must verify against current Telegram rules.
- Web uses `react-router-dom` v6 (BrowserRouter) + TanStack Query v5; no Zustand — server state lives in Query, the little UI state is local/hooks.
- `tg` facade is a Proxy over the real/mock implementation chosen once in `initTelegram()`; components never touch `window.Telegram`.
- Mock is selected by the build-time constant `import.meta.env.VITE_DEV_MOCK === "true"` and loaded through dynamic `import()` — Vite drops it (and MockUI/DevTools) from production bundles (verified by grepping `dist`); `vite.config.ts` additionally fails any production-mode build with the flag on.
- Mock identity (`mock_user`, `mock_premium`, `mock_platform`, `mock_lang`) is persisted in localStorage so SPA navigation and DevTools switches survive reloads; query params override it when present.
- Greeting/name displayed in UI comes from the server session (authoritative), not from client-side initDataUnsafe.
- Mock initData is signed at page load and is valid for 1h (server maxAge); the mock does not auto-refresh — reload the page after an hour.
- API base in the web app is same-origin `/api` (Vite proxy in dev, Fastify single-origin in prod); `VITE_API_URL` is optional.
- E2E uses its own SQLite file + upload dir, API on :3100 and web on :5273 (single origin via the Vite proxy), recreated on every run. The sandbox's preinstalled Chromium is used via `executablePath` (override with `PW_CHROMIUM`).
- Fonts: 6 self-hosted OFL families from @fontsource (latin + cyrillic subsets, one weight each; files + license texts in `apps/web/public/fonts`). Free: Inter, Manrope. Premium: Unbounded, Oswald, Playfair Display, Pacifico. Chosen because all cover Cyrillic — Bebas Neue / Space Grotesk (first draft) do not, and canvas would silently fall back for Russian titles.
- `document.fonts.load(font, sampleText)` is awaited with the real text before any drawing so the right unicode-range subset is fetched.
- Editor step 1 ("pick/create chain") happens on Home/Chain/Create screens; the editor opens with the chain already chosen and shows it in its header. Steps in the editor: Photo -> Style (pan/zoom + template/font picker) -> Publish (preview + caption).
- "#N" badge and participants counter both use `myPosition ?? postsCount + 1` (API returns `myPosition` so re-posting keeps the same number).
- Live preview is a 540x960 canvas drawn with the same `drawCard` as the export (scale 0.5); the attribution badge is a DOM overlay positioned like the server's (bottom-right, 220px above the bottom edge), shown to everyone.
- Export: JPEG q0.9, lowered stepwise (0.82/0.74/0.66) only if the blob exceeds 3 MB. Photos > 2560px on the longest side are downscaled right after decoding (EXIF handled by `createImageBitmap({imageOrientation:"from-image"})`).
- Pan/zoom model: `View = {zoom>=1, cx, cy}` (normalized source center) so the photo can never leave the frame; drag, pinch, wheel and a zoom slider (accessible) all go through the same pure helpers in `editor/layout.ts` (unit tested). Frame rotation (±3° on two templates) is ignored for drag math.
- The Editor chunk (canvas, fonts CSS, templates UI) is lazy-loaded; a test hook (`window.__storychain.render`) exists only when `VITE_DEV_MOCK=true`.
- Playwright sample photos are generated with `sharp` (root devDependency) so EXIF-rotated JPEGs can be produced deterministically.
- Known: main bundle is ~150 kB gzip (react-router, react-query, zod via shared); TonConnect will be code-split in Phase 5; further bundle work is in Phase 6.
- `widget_link` is Premium-only in Telegram Stories: it is passed only when `initDataUnsafe.user.is_premium` is true, the link is ALWAYS also in the caption text, and if shareToStory throws with a widget we retry once without it (we cannot reliably detect the rejection otherwise).
- `shareToStory` requires a public HTTPS media URL (blob/data URLs do not work) and client >= 7.8: below that (or on a throw) we fall back to opening/downloading the image + copying the link + an alert. `sharedToStory` is set only after a real shareToStory call, never for the fallback.
- Story text is capped at 200 chars (safe for non-Premium authors): the title is shortened first, the link is never cut. Length is counted in UTF-16 units (conservative vs. code points).
- Publishing auto-opens the story composer ("one tap"); the done screen and the chain page offer "Share again" and "Send to chat" (`t.me/share/url` via `openTelegramLink`) without re-posting; the API returns `myPost` and `shareLink` on `GET /chains/:id` for this.
- Bot: `/start` replies with a `web_app` inline button; `/start chain_<id>` opens `WEBAPP_URL/?tgWebAppStartParam=chain_<id>` (a web_app button cannot carry `startapp`, so the client's start_param fallback reads that query param). Invalid payloads fall back to the plain welcome. Telegram requires https for web_app buttons.
- The bot is started only when `BOT_ENABLED=true` (default on in production, off otherwise) so mock/dev needs no real token. Polling in dev (deletes any webhook first), webhook in prod at `POST /api/telegram/webhook` verified with the secret-token header (grammY `secretToken`). Handlers are unit tested by replacing the Bot API transport with a recorder.
- Mock: `showAlert`/`showConfirm` are DOM dialogs and `openTelegramLink` is a modal (scriptable in e2e); DevTools has a "Legacy client (<7.8)" switch to exercise the manual fallback.
- The clipboard write is raced against a 1.5s timeout: the Clipboard API can hang on a pending permission prompt and must never block the fallback alert.
- The Vite dev server allows any Host header (`allowedHosts: true`) so one tunnel to :5173 serves web + `/api` + `/uploads` through its proxy; this affects the dev server only.
- Payments are provider-agnostic at the ledger level (`payments/ledger.ts`): `settlePayment` runs `applyBoost` (conditional claim pending|expired -> paid + chain boost) in ONE DB transaction; `externalId` (Stars charge id / TON event id) is unique, so replays and double deliveries grant exactly once. Verified with concurrent-delivery tests.
- Stars: invoice link via `createInvoiceLink` (XTR, empty `provider_token`, one price item, `payload = reference`). `pre_checkout_query` is answered from one indexed DB lookup (no network) and validates status/expiry/amount/currency/user. `successful_payment` with a mismatching amount or user is NOT granted and is logged loudly (money moved: manual review). `refunded_payment` service messages revoke PRO; `scripts/refund.ts` (`pnpm --filter @storychain/api refund <reference|chargeId>`) calls `refundStarPayment` first, then revokes locally.
- The client's `openInvoice` status is never trusted: after `paid`/`pending` the boost sheet polls `GET /api/payments/:reference` (Stars 20 s, TON 150 s). A timeout is shown as "still processing" with a re-check button, not as failure.
- Without a bot (mock/dev) the invoice URL is `mock-invoice://<reference>`; the mock dialog's "Pay" goes through `POST /api/dev/payments/:reference/complete`, which calls the SAME `handleSuccessfulPayment` code as the bot (so amount/user validation is exercised). For TON the dev endpoint settles directly (it stands in for "the verifier matched an on-chain transfer").
- TON verification: a transfer pays a transaction iff comment == reference, status ok, jetton master and recipient equal in RAW form (`Address.parse(..).toRawString()`, so bounceable/non-bounceable/testnet spellings are equal), amount >= expected (overpay accepted, underpay stays pending), tx hash not used before, and timing is sane. Event timestamp must not precede the order (minus 5 min skew).
- Late TON payments: a transfer after `expiresAt + 5 min skew` is still honored (and logged as late) if it happened within 24 h of expiry — the user paid real money and refusing would strand it; beyond that the tx stays `expired` and is only logged for manual handling. `expired` is a status (set by the polling job / shown by the API), not a tombstone.
- The poller (`setInterval` 10 s, shared in-flight promise as overlap guard) skips the indexer entirely when no TON order is open, to save TonAPI quota. It looks back to the oldest open order, up to 5 pages x 100 events. `POST /payments/ton/confirm` runs the same tick immediately (BOC is informational only, never trusted).
- TonAPI endpoints/response shapes used (ASSUMPTION — re-verify against current TonAPI docs and with the manual mainnet test): `GET /v2/accounts/{merchant}/jettons/{master}/history` (AccountEvents with `JettonTransfer` actions; `event_id` is used as the tx hash / idempotency key), `GET /v2/accounts/{owner}/jettons/{master}` (-> `wallet_address.address`), `GET /v2/jettons/{master}` (-> `metadata.decimals/symbol`). All sit behind the `TonIndexer` interface (`payments/tonIndexer.ts`); parsing is unit-tested on fixtures.
- GRAM is assumed to follow TEP-74: an ordinary transfer with `forward_ton_amount > 0` makes the merchant's Jetton wallet emit a transfer notification carrying the forward payload (our reference). If GRAM (a PoW jetton) deviates, comment matching would fail — hence the manual small mainnet test transfer in `CHECKLIST.md`.
- Startup self-check (`tonStartupCheck.ts`): runs only when a merchant address is configured and not in mock mode. It parses addresses with `@ton/core`, refuses to start if the jetton's on-chain `decimals` differ from `GRM_DECIMALS`, and only warns on symbol mismatch.
- Only `@ton/core` is used (cell building/parsing); `@ton/ton` was not needed, so it is not a dependency. The browser needs a `Buffer` polyfill (`ton/polyfill.ts`), imported first by every TON module.
- Client payload: ONE message to the sender's own Jetton wallet (0.05 TON gas) with body `transfer#0f8a7ea5` (query_id random uint64, amount, destination = merchant OWNER address, response_destination = sender, no custom payload, forward_ton_amount 0.01 TON, forward payload = Either-ref text comment `0x00000000 + reference`), `validUntil` = now + 10 min; tested by decoding the BOC back.
- The sender's Jetton wallet is resolved by the backend (`GET /api/ton/jetton-wallet`, cached 10 min per raw owner address) so no third-party API key ever reaches the browser. TonConnect and `@ton/core` live in a lazy chunk used only on the paywall and only in non-mock builds; the mock build uses a simulation panel instead.
- `tonconnect-manifest.json` is generated from `WEBAPP_URL` by `predev`/`prebuild` (wallets need the real public origin) and is git-ignored; `iconUrl` points at `/icon-180.png`.
- Platform policy flag: `TON_PAYMENTS_ALL_PLATFORMS=false` => Stars only on ios/android (enforced by `/api/plans` AND `/api/payments/ton/intent`, so the policy cannot be bypassed by calling the API directly). The owner must verify against current Telegram rules for digital goods in Mini Apps.
- E2E additionally runs a second Vite server with `VITE_DEV_MOCK=false` and a fake `window.Telegram.WebApp`, so the real (non-mock) facade and lazy TonConnect chunk are exercised on every run.
- Single-origin mode: with `SERVE_WEB=true` (default in production) Fastify serves `apps/web/dist`, falls back to `index.html` for non-`/api`, non-`/uploads` GETs (client-side routes / deep links) and keeps unknown `/api/*` as JSON 404s. It refuses to start if the build is missing. Static assets are exempt from the rate limiter (many files per load, shared NAT IPs).
- CSP in single-origin mode: `script-src 'self' https://telegram.org` (the SDK), inline styles allowed (React style props + TonConnect), `img-src https: data: blob:`, `connect-src 'self' https: wss:` (wallet bridges), `frame-ancestors 'self' https://web.telegram.org https://*.telegram.org`; `X-Frame-Options` is disabled because it cannot express the Telegram Web allowance (Mini Apps are iframed there). `upgrade-insecure-requests` only in production so plain-http local runs work.
- `INITDATA_MAX_AGE_SEC` defaults to 24 h (the pure `validateInitData` keeps the spec's 3600 s default): Telegram does not refresh `initData` while a Mini App stays open, so a 1 h window logs people out mid-session. The trade-off is a longer replay window for a leaked header; tighten it if you prefer.
- `TRUST_PROXY` is opt-in so a spoofed `X-Forwarded-For` cannot dodge IP rate limits when the API is directly exposed.
- `pnpm build` forces `VITE_DEV_MOCK=false` (cross-env) so a dev `.env` can never produce a production build with the mock, while a direct `vite build` with the flag on still fails loudly (guard kept in `vite.config.ts`). `pnpm smoke` greps the built bundle for mock/test-hook markers.
- The web app imports `@storychain/shared/light` (everything except the zod schemas), saving ~7% of the main bundle; client-side chain validation mirrors the server schema through `normalizeChainInput` (a unit test asserts they agree). The server keeps using the full `@storychain/shared`.
- The TonConnect chunk loads only after the user taps "Pay with GRM" (and is preloaded on hover/focus), so Stars-only users never download it.
- A11y: axe (WCAG 2 A/AA) runs in e2e over Home (with the Hot carousel), Chain, Create, the Boost sheet, Profile and Editor in light and dark; it found sub-4.5:1 hint/button/link colors in the fallback palette and the mock theme, which were darkened. Real Telegram themes bring their own colors, so contrast there is Telegram's responsibility.
- Mobile layout is asserted at 390×844 with touch emulation (no horizontal overflow on every screen; editor preview ≤ 60% of the viewport height, 9:16 preserved).
- Profile ("My posts") is a minimal screen backed by `GET /api/me/posts` (offset cursor, hidden posts/chains excluded) reachable from the avatar on Home.
- `pnpm bootstrap` (scripts/setup.mjs) is the one-command setup (NOT `pnpm setup`: that is a built-in pnpm command that configures pnpm itself and would silently shadow it; the Prisma client is also generated by the root `postinstall`): `.env` from the example (mock mode), Prisma generate, migrate, seed.

## Pivot: free viral loop + paid Marathon Boosts

- Phases 1–4 of the pivot intentionally left `apps/web` (and the old API tests) red while the backend moved first; each package was brought green in the phase that owns it and the intermediate commits are not individually green. The final commit of every phase from 5 on passes `typecheck`, `lint`, `test` and `build`.
- Only the **creator** of a chain can boost it (Stars invoice / TON intent return 403 otherwise; the UI hides the button). A paid placement is bought by the person who owns the marathon, never by a stranger.
- `Chain.boostedUntil` is the **source of truth** (`boostedUntil > now`); `Chain.isBoosted` is a denormalized cache. Every query and DTO uses `boostedUntil > now`; the 60 s sweeper only refreshes the cache and nothing depends on it (tests prove a stale `isBoosted = true` is harmless).
- The clean "StoryChain" attribution badge is composited **server-side for every user** (the client never bakes it in); `Post.watermarked` is kept and is now always `true`.
- Posting is unlimited and every template/font is free. **Anti-spam rate limits remain** (posts 20/min, chains 10/hour, reports 10/hour, all env-configurable, keyed per user); they answer `RATE_LIMITED` (429) with a friendly "you're going a bit fast" message and never mention plans, quotas or payment.
- `channelUrl` accepts only `t.me/<name>`, `https://t.me/<name>`, `http://t.me/<name>` (→ https), `@name`, `https://t.me/+<hash>` and `https://t.me/joinchat/<hash>` (username 5–32 chars `[A-Za-z0-9_]`, starts with a letter; reserved single-segment paths like `joinchat`/`share` rejected; max 100 chars; no query/fragment/userinfo/extra path; no inner whitespace). Surrounding whitespace is trimmed because mobile keyboards add it; an empty string means "no channel".
- `channelUrl` is **publicly visible only while the chain is boosted**; the creator always sees their own. `boostedUntil` (the remaining time) is returned to the creator only and never shown publicly.
- Paid placements are always labelled **"Sponsored" / "Реклама"** (carousel cards, chain page, list items).
- Boost price **placeholders** (the owner MUST set real ones): Stars 100 / 500 (`STARS_BOOST_24H_PRICE`, `STARS_BOOST_7D_PRICE`), GRM 50 / 250 (`GRM_BOOST_24H_PRICE`, `GRM_BOOST_7D_PRICE`, human amounts → bigint via `toUnits`, must be > 0 and fit `GRM_DECIMALS`).
- Boosts **stack** from the current end (`start = max(now, boostedUntil)`) with an optimistic-concurrency write so two concurrent purchases cannot lose an extension; the horizon guard (`BOOST_MAX_HORIZON_DAYS`, default 30) rejects purchases whose end would be too far in the future (`BOOST_HORIZON_EXCEEDED`), re-checked in `pre_checkout`.
- `ChainBoost.txId` = the Transaction id (unique): one boost per paid transaction, which is what makes redelivery/replay idempotent. A refund deletes the row and subtracts exactly its duration (`boostedUntil` becomes null when nothing is left).
- **Paid, then the chain became hidden/deleted** (between payment and fulfilment): the transaction is still marked `paid`, **no boost is created**, `rawJson` gets `"note": "chain_not_boostable"` and a warning is logged. This needs a **manual refund** (Stars: `scripts/refund.ts`; GRM: by hand). Same for a late payment of an old legacy order (`unknown_plan`).
- Legacy data: the `boosts_pivot` migration sets pending transactions of the removed legacy plan to `expired` and leaves paid ones untouched as history (`Transaction.chainId` is nullable for them). The migration test replays the real SQL on a pre-pivot database. Tests build the legacy identifiers from parts (`test/legacy.ts`) so the repo-wide "removed vocabulary" grep stays clean without losing the tests' meaning.
- "Hot" carousel = active (`boostedUntil > now`), non-hidden chains ordered by `boostedUntil` desc, max 10, requires auth like every other endpoint; the Home feed (`/api/chains`) keeps its ordering but items carry `isBoosted`.
- The boost sheet is lazy-loaded (with the TonConnect bits); the channel link is validated client-side (same shared parser) and saved through `PATCH /api/chains/:id` **before** any payment starts. The title is intentionally not editable (it is printed on cards already shared).
- Dev/mock: `POST /api/dev/boost-chain {chainId, hours}` and `POST /api/dev/expire-boost {chainId}` (which deliberately leaves the cached flag untouched to prove the API relies on `boostedUntil`). The dev `init-data` body field is now `isTgPremium`.
- Renamed the production flag in `config` to `inProduction` because the old name collided, as a substring, with the repo-wide grep for the removed vocabulary.
- The Stars-for-digital-services policy and the per-platform GRM flag (`TON_PAYMENTS_ALL_PLATFORMS`, Stars-only on iOS/Android) are unchanged and must still be verified by the owner against Telegram's current rules (a promoted placement may be treated as a digital service).

## Security & performance audit

Findings, evidence and what is left for the owner are in [`AUDIT.md`](./AUDIT.md). Decisions taken while fixing them:

- **`initData` validation is unchanged**: it already followed Telegram's algorithm (HMAC-SHA256 keyed by `HMAC("WebAppData", bot token)`, every field except `hash` - including newer ones such as `signature` - in the data-check string, constant-time comparison, strict `auth_date`). It now has direct unit tests (tampering, smuggled duplicate fields, hash shape, age window boundaries, user shape) that were mutation-checked.
- **The 24 h `initData` window stays** (`INITDATA_MAX_AGE_SEC`): Telegram never refreshes `initData` during a session, so a shorter window would log people out mid-use. The cost is that a leaked `initData` is a 24 h bearer credential; lower the value if that matters more. When the server stops accepting it the UI shows one "reopen the app" screen instead of an error per section.
- **A placeholder bot token cannot run in production**: `BOT_TOKEN` must look like `<id>:<35 chars>`, because the HMAC key for `initData` is the token and the one in `.env.example` is public. `WEBAPP_URL` and `TONCONNECT_MANIFEST_URL` must be https in production.
- **`DEV_MODE` is refused on non-local `WEBAPP_URL` / `PUBLIC_BASE_URL`** (override: `ALLOW_REMOTE_DEV_MODE=true`; the test environment is exempt). Its endpoints mint valid logins, so a public host that merely forgot `NODE_ENV=production` must not start.
- **A webhook without a secret never exists**: webhook mode needs `WEBHOOK_URL` + `WEBHOOK_SECRET` whenever the bot is enabled, in every environment, and the route refuses to register without one (a forged `successful_payment` update would grant a boost).
- **TonAPI pages are parsed event by event.** Anyone can send GRM to the merchant address, so one odd event must not stall every pending payment: unreadable events/actions are skipped, counted and logged (`skipped`), a response that is not an event list at all still fails the poll.
- **Each transfer is processed in isolation** and `tick()` never rejects (the interval calls `void tick()`; a rejection would crash the process). A transfer that failed is simply seen again on the next poll.
- **Orders are looked up in bulk, and only for comments shaped like our references** (`[A-Za-z0-9]{8,32}`): free-text comments from random senders never reach the database.
- **Late-payment candidates are polled once a minute** (`GRACE_POLL_INTERVAL_MS`) instead of every 10 s; any live order restores the fast cadence immediately. A truncated history window (all 5 pages full) logs a warning because spam could hide a real payment beyond it.
- **`confirm` is rate-bounded**: `TonVerifier.nudge()` runs at most one extra poll per 3 s, however many users press it, and never leaves a timer behind. The Jetton-wallet cache is bounded (1000 entries, 10 min).
- **0.1 TON is attached to the Jetton transfer** (was 0.05) with the 0.01 TON forward amount unchanged: the reference Jetton wallet bounces (exit 709) unless the attached value exceeds forward + forward fees + 2 x gas + a storage reserve, which with this forward amount is roughly 0.041 TON for one version of the reference contract and 0.051 TON for another (the constants differ between versions), so 0.05 was marginal at best and other implementations reserve more. Whatever is unused returns to the payer (`response_destination`). **Verify on testnet** (CHECKLIST).
- **The network is part of the contract**: the server says which network it watches; the client refuses a wallet on another one before any order exists and demands the network in the TonConnect request. The payer's Jetton wallet is resolved _before_ the order is created, so "no GRM" / "wrong network" leave nothing behind (an abandoned order also kept the verifier polling for the whole 24 h grace window).
- **After the wallet has signed, the client never reports a failure**: a failing `/confirm` (rate limit, network) is swallowed because the status is polled anyway - showing "failed" for a transfer that is on its way makes people pay twice.
- **A second, different Stars charge for an already paid order is refunded automatically** (`refundStarPayment`), logged loudly, and the user is told; if the refund call fails the log names the charge for a manual refund. The same charge arriving again (redelivery) stays an idempotent no-op. The later `refunded_payment` for that charge is logged as a warning, not an error, because it was never an order's payment. The dev "complete" endpoint uses one charge id per order so completing twice behaves like a redelivery.
- **Keyset cursors replace OFFSET** (`newest`: `<createdAtMs>.<id>`, `trending`: `<postsCount>.<createdAtMs>.<id>`): O(page) instead of O(offset), and stable while rows are added or re-ranked. Cursors are parsed strictly (anything else is a 400); the client treats them as opaque and de-duplicates by id anyway. Consequence: an item that overtakes the scroll position is skipped for that scroll, never shown twice.
- **Indexes carry the whole predicate** (`isHidden` / `isFeatured` / `creatorId` are part of the composite indexes), so the right index wins even on SQLite without planner statistics. Measured on 50k chains / 100k posts: trending feed 10.7 -> 0.1 ms, "new" 30 -> 0.1 ms, My marathons 4.6 -> 0.1 ms, My posts 9.3 -> 0.1 ms, a deep page 78 -> ~0.2 ms. The old `[isFeatured, createdAt]` index is superseded.
- **A replaced card is deleted from storage** (and so are files whose database write failed): the old URL was public forever, which is a privacy problem when someone replaces a card because it showed something it should not have, and storage grew without bound. Cleanup failures are logged, never surfaced. Uploads are served `immutable` because every file has a fresh random name.
- **Graceful shutdown**: the old signal handlers stopped timers, which also removes Node's default "terminate", so the process kept serving and ignored `SIGTERM` until the orchestrator killed it. The new module stops background work, drains the HTTP server (sweeping idle keep-alive connections, since `close()` alone waits out Fastify's 72 s keep-alive timeout), closes the database and exits, with a 10 s watchdog.
- **The served TonConnect manifest must match `WEBAPP_URL`** when TON payments are on outside mock mode: a build made without `WEBAPP_URL` silently ships a `localhost` manifest and every wallet then rejects GRM payments with no server-side hint.
- **Client**: every request has a timeout (15 s, 60 s for uploads, covering the body); queries retry only network errors and 5xx, never a 4xx; `POST /auth/session` no longer gates the first render (the feeds authenticate by themselves) and is refreshed every 10 min; plans are cached for 10 min and prefetched for creators; payment polling eases off 1.5 s -> 6 s and stops on answers that cannot change; the card preview repaints only when the card changes; React/router/query are a separate `vendor` chunk (~72 kB gzip) so a deploy only invalidates the ~15 kB app entry.
- **The web build forces `NODE_ENV=production`.** Vite takes `NODE_ENV` from the root `.env` (`envDir` is the repo root) and the default `.env` says `development`, which silently produced a development build of React (131 kB vs 72 kB gzip for the vendor chunk, and slower at runtime). `pnpm smoke` and CI now fail if the bundle contains React's development-only DevTools hint.
- **Dependencies**: `@fastify/static` 10.1.5 and `react-router-dom` 7.18 (production advisories), vitest 4.1 (4 critical dev advisories incl. tinypool), `shell-quote` pinned >= 1.11 via `pnpm.overrides`. Left alone because there is no upstream fix and they are dev-time only: `deepmerge-ts` (Prisma CLI config merge), `braces` and `postcss-selector-parser` (Tailwind 3).
- **Accepted, not changed**: the TON verifier trusts one indexer (TonAPI) - a second source or a confirmation depth would be the next step; `X-TG-Platform` is client-controlled, so the iOS/Android "Stars only" rule is a policy hint, not a security boundary; the in-memory rate limiter and the TON poller are per process; CSP keeps `style-src 'unsafe-inline'` because React emits inline style attributes (`script-src` stays strict); the auth hook does one indexed `SELECT` per request.

## Pre-launch adversarial review

- **Refunds use compare-and-set.** `revokeBoost` read `boostedUntil`, subtracted the refunded duration and wrote the result unconditionally. Under PostgreSQL's READ COMMITTED a purchase committed between that read and write was erased (paid, and the boost silently lost). It now retries on a changed value exactly like `applyBoost`; a deterministic interleaving test proves it.
- **Refund arithmetic (policy, unchanged, now tested for stacks):** a refund removes exactly the refunded boost's full duration from the chain's end, regardless of how much of it has been used, and the end never lands in the past (`null` instead). With 24h + 7d stacked, refunding the 24h after it ran out still shortens the chain by 24h: the refund takes back what it bought.
- **User text is sanitized before any length check** (`sanitizeText`, used by every schema and by the client): NFC, bidi embeddings/overrides/isolates and direction marks, zero-width space / word joiner / BOM and C0/C1 control characters are removed, line breaks become spaces (descriptions and report reasons keep single line breaks). A title made only of zero-width spaces used to pass the 3-character minimum, and an RLO in a title reversed the "Join: <link>" text after it in story captions and the Stars invoice. ZWJ, ZWNJ, variation selectors and tag characters stay (emoji families, Persian spelling, subdivision flags). Titles stored before this are cleaned where text leaves the app (card canvas, story text, invoice).
- **Text is shortened by grapheme, not by UTF-16 unit**: the card's ellipsis and the story-text truncation could split an emoji into a lone surrogate (rendered as a replacement glyph).
- **Orphaned local uploads are recoverable**: `pnpm --filter @storychain/api gc-uploads [--delete]` lists/removes files under `posts/` that no post references and that are older than 24 h (an upload in progress writes its files moments before its post exists). Matching is by storage key, never by full URL, so a change of `PUBLIC_BASE_URL` cannot make every file look orphaned. S3 deployments need a bucket-side job instead.
- **CSP directives that matter are pinned exactly in tests** (`frame-ancestors`, `script-src`, `object-src`, `base-uri`, no `unsafe-eval`), on the SPA shell, deep links and assets; the API alone answers `X-Frame-Options: SAMEORIGIN`.
- **Reviewed and left as is**: two processes settling the same TON transfer concurrently grant exactly once (conditional `pending|expired -> paid` claim, unique `externalId`, unique `ChainBoost.txId`; tested with two DB connections). TON has deterministic (BFT) finality and TonAPI's unfinished traces (`in_progress`) are skipped, so there is no probabilistic reorg window to wait out; a confirmation delay would only add latency. Keyset cursors are a strict total order (`createdAt`, then the unique `id`); `ORDER BY` and the cursor comparison use the same column collation, so identical timestamps cannot collide or reorder. Amount handling has no float paths: `toUnits` accepts only `\d+(\.\d+)?`, on-chain amounts must be all digits before `BigInt`, Stars amounts are compared as strings of integers.
